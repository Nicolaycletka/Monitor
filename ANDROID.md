# Автономный APK для Android

Обёртка Capacitor. Фронтенд лежит ВНУТРИ приложения, на сервер уходит
только синхронизация. Работает офлайн полностью: интерфейс, расчёты,
дневник в IndexedDB — всё локально, сеть нужна лишь чтобы обменяться
записями с сервером и другими телефонами.

## Что за собой потянула автономность

Четыре вещи, и каждая ломается молча, если её забыть.

**1. Адрес API.** В вебе он относительный — приложение и API отдаёт
один сервер. В APK файлы открываются с origin `https://localhost`, а
сервер живёт на другом домене, поэтому адрес задаётся при сборке через
`VITE_API_URL`. Наличие этой переменной служит признаком «сборка
автономная» и для остального кода: отдельный флаг заводить не стали,
два флага рано или поздно разъедутся.

**2. CORS.** Каждый запрос из APK — межсайтовый, без разрешения сервера
не пройдёт ни один. Список источников закрытый, задаётся переменной
`CORS_ORIGINS` (по умолчанию `https://localhost,capacitor://localhost`).
Отражать присланный Origin обратно нельзя: токен ездит в заголовке, и
любой сайт смог бы дёргать API от имени пользователя. Куки не
используются, поэтому `credentials` не разрешаем и CSRF взяться неоткуда.

**3. Service worker не регистрируется.** Он кеширует то, что иначе
пришлось бы тянуть по сети; в APK файлы и так внутри, а его кеш
оболочки начал бы конкурировать с ними за то, что показать.

**4. Самообновление превращается в предупреждение.** В вебе расхождение
сборок лечится перезагрузкой. В APK перезагрузка поднимет ровно те же
файлы — и так на каждом выводе приложения на передний план, вечно.
Поэтому здесь расхождение не перезагружает, а показывает плашку «вышла
новая версия, попросите свежий APK».

Это важнее, чем кажется. Устаревший клиент опасен тем, что снаружи
неотличим от исправного: именно так пуши о вехах приходили со старым
текстом, и на поиск ушёл целый раунд. В автономном APK такой клиент
неизбежен — телефон бабушки не обновится сам никогда. Плашка не чинит
проблему, но делает её видимой.

## Что нужно на машине сборки

**JDK 17** — именно 17, не новее. Шаблон Capacitor 6 закреплён на
Gradle 8.2.1 и Android Gradle Plugin 8.2.1: Java 21 они не понимают,
сборка падает с «Unsupported class file major version». Поднимать
версии ради новой Java смысла нет, а риск сломать сборку есть.

Ещё нужны Android SDK (platform 34, build-tools 34) и Node 20+.

В контейнере, где это готовилось, APK получить нельзя: Gradle тянет
дистрибутив и зависимости с `services.gradle.org` и `dl.google.com`,
доступа туда нет. Проверено, а не предположено. Проект, иконки и
конфигурация готовы полностью.

## Сборка на GitHub, без локальных инструментов вообще

`.github/workflows/android.yml`. Виртуальная машина GitHub уже содержит
Android SDK и Java, поэтому ставить на своей машине не нужно ничего —
ни JDK, ни SDK, ни Node.

Запуск: вкладка Actions → «APK для Android» → Run workflow. Готовый
файл появится внизу страницы запуска, в разделе Artifacts. Если
поставить тег вида `v1.3`, сборка запустится сама и приложит APK к
релизу — у файла будет постоянная ссылка, которую можно просто
отправить родственникам вместо пересылки файла каждому.

На каждый push сборка НЕ запускается намеренно: APK нужен не после
каждой правки, а когда его собираются кому-то отдать.

### Ключ подписи обязателен, и вот почему

Без ключа конвейер соберёт отладочный APK. Он ставится и работает, но
у каждой такой сборки **своя случайная подпись**: отладочное хранилище
ключей создаётся на чистой машине заново при каждом запуске. Android не
даёт обновить приложение, подписанное другим ключом, — значит каждый
раз придётся удалять и ставить заново, теряя локальную базу на
телефоне. Записи вернутся с сервера, но переподключаться по приглашению
придётся каждому.

Поэтому ключ заводится один раз:

    keytool -genkey -v -keystore monitor.keystore -alias monitor \
      -keyalg RSA -keysize 2048 -validity 10000

    base64 -w0 monitor.keystore    # в Windows: certutil -encode

Полученную строку и пароли положить в Settings → Secrets and variables
→ Actions:

    ANDROID_KEYSTORE_BASE64      содержимое base64
    ANDROID_KEYSTORE_PASSWORD    пароль хранилища
    ANDROID_KEY_ALIAS            monitor
    ANDROID_KEY_PASSWORD         пароль ключа

Сам файл `monitor.keystore` в репозиторий класть НЕЛЬЗЯ и терять тоже
нельзя — восстановить его неоткуда, а без него обновления кончатся
навсегда. Храните копию отдельно от репозитория.

Подпись подключается в `android/app/build.gradle` через свойства
проекта. Если свойств нет, блок подписи не создаётся вовсе и
`assembleRelease` выдаст неподписанный APK — это лучше, чем молча
подписать чем попало: неподписанный Android просто не поставит, и
ошибка будет видна сразу.

### Чего эта часть не проверена

Конвейер написан, но ни разу не запускался: в контейнере, где он
готовился, нет доступа ни к GitHub, ни к Android SDK. Синтаксис YAML,
имена скриптов и скобки в gradle-файле сверены, всё остальное —
по документации. Первый запуск может потребовать правок, чаще всего
в шаге установки SDK.

## Windows 11 без прав администратора

Собирается целиком, ничего ставить в систему не нужно: все три
зависимости распространяются zip-архивами, а Gradle качает себя сам в
профиль пользователя.

Разложить в короткие пути БЕЗ кириллицы и пробелов — например
`C:\dev\jdk17`, `C:\dev\node`, `C:\dev\android-sdk`, проект в
`C:\dev\bt`. Это не педантизм, а обход двух вещей, которые без
администратора не лечатся:

* **Лимит пути в 260 символов.** Android-сборка создаёт очень глубокие
  каталоги, а снятие лимита правится в реестре или групповых политиках,
  то есть требует прав. Единственная защита — начинать от корня диска.
* **Кириллица в имени пользователя.** Если профиль
  `C:\Users\Василий`, часть инструментов спотыкается о путь к кешу.
  Поэтому `GRADLE_USER_HOME` и SDK выносятся из профиля.

Переменные окружения задаются в разделе «Переменные среды **для
пользователя**» — права там не нужны. Открывается без панели
управления: `Win+R` → `rundll32 sysdm.cpl,EditEnvironmentVariables`.

    JAVA_HOME         C:\dev\jdk17
    ANDROID_HOME      C:\dev\android-sdk
    GRADLE_USER_HOME  C:\dev\gradle
    Path              += C:\dev\jdk17\bin;C:\dev\node;C:\dev\android-sdk\platform-tools

**Path правьте именно этим окном, не через `setx`.** `setx` обрезает
значение на 1024 символах и молча портит существующий Path — вернуть
его потом неоткуда.

Командные инструменты SDK распаковываются с обязательной вложенностью:
исполняемые файлы должны оказаться в
`C:\dev\android-sdk\cmdline-tools\latest\bin`, иначе `sdkmanager`
не найдёт себя сам. Дальше:

    sdkmanager --licenses
    sdkmanager "platform-tools" "platforms;android-34" "build-tools;34.0.0"

Всё скачивается внутрь `C:\dev\android-sdk`, права не нужны.

Что действительно потребовало бы администратора — драйверы USB для
`adb`. Они не нужны: готовый APK переносится на телефон как обычный
файл, через кабель в режиме передачи файлов, мессенджер или облако.

Если включена «Контролируемый доступ к папкам» в Защитнике, она
охраняет «Документы» и «Рабочий стол», а исключения добавляются только
с правами. Ещё одна причина держать всё в `C:\dev`.

## Сборка

    npm install
    cd web && npm install && cd ..
    npm run android:build      # собирает фронтенд с абсолютным API и синхронизирует
    npm run android:apk        # ./gradlew assembleDebug

APK окажется в `android/app/build/outputs/apk/debug/app-debug.apk`.
Его можно скинуть в мессенджер и поставить на любой Android, разрешив
установку из неизвестных источников. Google Play не нужен.

Адрес сервера зашит в `package.json`, в скрипте `android:build`. Меняете
домен — правьте там же и не забудьте `CORS_ORIGINS` на сервере.

### Подписанная сборка

    keytool -genkey -v -keystore monitor.keystore -alias monitor \
      -keyalg RSA -keysize 2048 -validity 10000

и прописать хранилище в `android/app/build.gradle`, дальше
`./gradlew assembleRelease`.

**Ключ нельзя терять.** Обновить приложение, подписанное другим ключом,
Android не даст: придётся удалять старое и ставить заново, а с ним
уедет локальная база. Записи вернутся с сервера, но переподключаться по
приглашению придётся заново.

Исходники в `assets/`, сделаны из `web/public/icon-512.png`:

## Приглашения: ввод кода руками

Ссылка приглашения ведёт на сайт и откроется в браузере, а не в
приложении. Перехват ссылок (Android App Links) требует
`assetlinks.json` на `https://burmalda.host/.well-known/` с отпечатком
ключа подписи — то есть работает только для подписанной сборки и
ломается молча, если отпечаток разъедется.

Поэтому на первом экране есть поле «Код приглашения»: туда вставляется
и голый код, и целая ссылка. Работает всегда. App Links можно добавить
потом — это улучшение, а не условие работы.

## Если захочется обратно к тонкой обёртке

Вернуть `"url": "https://burmalda.host/monitor/"` в блок `server`
файла `capacitor.config.json` и собирать фронтенд без `VITE_API_URL`.
Тогда обновления прилетают деплоем, как в вебе, но офлайн держится
только на service worker и кеше WebView.

## Постоянное уведомление с кнопкой «Заснул» / «Проснулся»

Нативная часть — один файл плагина и правка `MainActivity`, около 230
строк. Приёмника broadcast больше нет.

### Кнопка открывает приложение, а запись делает JavaScript

Первый вариант был другим: фоновый приёмник отправлял запись прямо на
сервер, приложение не открывалось. От него отказались в пользу
запуска приложения, и вот почему.

* **Работает без сети.** Запись ложится в местную базу и уедет на
  сервер при первой возможности. Фоновая отправка без связи просто
  теряла бы отметку — а ночью связь в квартире как раз и подводит.
* **У отметки один путь в дневник.** Кнопка в уведомлении и кнопка на
  экране вызывают одни и те же `putEvent` и `runSync`. Двух веток,
  которые надо держать согласованными, не существует.
* **Токен никуда не сохраняется.** Фоновому приёмнику он был нужен,
  чтобы авторизоваться на сервере; приложению — нет.
* **Нативного кода втрое меньше**, а это ровно та часть, которую здесь
  труднее всего проверить.

Цена: приложение видимо открывается, и на заблокированном телефоне
система потребует разблокировки. Если это окажется неудобно ночью,
запасной вариант — вернуть фоновую отправку, оставив запуск приложения
только на случай отсутствия сети.

### Как пометка доезжает до JavaScript

Через SharedPreferences, а не событием в мост Capacitor. Событие
потребовало бы, чтобы мост уже был готов в момент прихода интента, а
при холодном запуске это не так: активность создаётся раньше, чем
WebView успевает загрузить приложение. Пометка, положенная на диск,
дождётся кого угодно и в любом порядке — гонок здесь нет по построению.

Плагин гасит пометку в тот же момент, когда отдаёт её. Иначе повторный
вызов (перезагрузка WebView, возврат из фона) применил бы одну отметку
дважды. Потерять пометку при сбое менее вредно, чем записать лишний
сон, который потом придётся искать и удалять.

Время нажатия кладётся в интент и используется как момент сна. Запуск
занимает секунду-другую, и записывать сон моментом готовности WebView
значило бы врать на эту секунду при каждой отметке.

Приложение проверяет пометку при запуске и при каждом возврате на
передний план: оно могло быть уже открыто, тогда холодного старта не
будет вовсе.

### Защита от двойной записи

Перед применением пометки приложение смотрит на своё состояние. «Заснул»
при уже открытом сне игнорируется, «Проснулся» при отсутствии открытого
— тоже. Уведомление и экран обновляются не мгновенно, и рассогласование
на секунду возможно; лучше проигнорировать лишнее нажатие, чем завести
второй сон.

### Это единственная непроверенная часть проекта

Нативный код не собирался и не запускался ни разу: здесь нет ни Android
SDK, ни компилятора Java — даже синтаксис проверить нечем. Всё остальное
в проекте стоит на прогонах, это — нет.

Что проверено: обёртка `web/src/sleep-notification.js` безвредна без
плагина (`tools/smoke-sleepnote.mjs`), веб-сборка не задета, все шесть
остальных дымовых тестов проходят. При любой поломке нативной части
приложение продолжит работать как раньше, просто без уведомления.

Чего ждать при первой сборке: ошибок компиляции в Java — самое
вероятное. Второе — уведомление не появится из-за разрешения
POST_NOTIFICATIONS: на Android 13+ его мало объявить в манифесте, надо
запросить у пользователя, а запроса пока нет.
