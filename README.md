# Дневник сна

PWA для отслеживания сна, кормлений и подгузников, с синхронизацией между
двумя родителями. Разворачивается на своём VPS одной командой.

Работает офлайн: всё пишется в IndexedDB на телефоне, синхронизация фоновая.
Если сервер лежит или в квартире нет интернета — приложение продолжает
работать, записи уедут позже.

## Что нужно

- VPS с Docker и Docker Compose
- домен, направленный на этот VPS (A-запись)
- nginx и certbot на хосте

HTTPS обязателен: без него Android не предложит установить приложение
и не запустит service worker.

## Установка рядом с существующим сайтом

Приложение живёт в подкаталоге и не трогает корень сайта. Порт — 8090,
потому что 8080 часто занят под masquerade.

```bash
git clone <ваш-репозиторий> baby-tracker
cd baby-tracker
docker compose up -d --build
curl -s http://127.0.0.1:8090/monitor/api/health   # {"ok":true}
```

Дальше добавьте в **существующий** server-блок, который отдаёт сайт
на 443 TCP, содержимое `nginx/monitor-location.conf` и перечитайте
конфигурацию:

```bash
sudo nginx -t && sudo systemctl reload nginx
```

Префикс задаётся в двух местах и должен совпадать: `BASE_PATH` в
`docker-compose.yml` (аргумент сборки и переменная окружения) и путь
в location-блоке. Меняете `/monitor` на другое — пересоберите образ:
`docker compose up -d --build`.

Чтобы развернуть в корне отдельного домена, поставьте `BASE_PATH: /`
в build args и `BASE_PATH=` (пустым) в environment.

## Установка на телефон

Откройте `https://ваш.домен/monitor/` в Chrome на Android → меню →
«Установить приложение».
Появится иконка на домашнем экране, приложение запустится в полный экран
без адресной строки.

На iOS: Safari → «Поделиться» → «На экран "Домой"». Работает, но iOS
агрессивнее чистит хранилище у редко открываемых приложений — держите
резервную копию.

## Второй родитель

Вкладка «Неделя» → «Поделиться ссылкой». Второй телефон открывает ссылку,
подключается к тому же дневнику и видит те же записи.

Ссылка работает и на телефоне, где приложение уже настроено: появится
экран подтверждения. Локальные записи при подключении не затираются —
они уезжают на сервер и сливаются с тем, что там есть, по правилу
«последняя запись побеждает». Идентификаторы записей уникальные,
поэтому повторное подключение по той же ссылке дублей не создаёт.

**Ссылка — это и есть пароль.** Кто её получил, тот имеет полный доступ
к дневнику. Токен лежит во фрагменте URL (после `#`), поэтому на сервер
в запросах он не уходит и в логи nginx не попадает — но в истории браузера
остаётся. Отзыва ссылки нет: если она утекла, заводите новый дневник
и переносите данные резервной копией.

## Разработка

```bash
cd server && npm install && DATA_DIR=./data npm start   # :8080
cd web && npm install && npm run dev                    # :5173, /api проксируется
```

## Как устроена синхронизация

Local-first. Каждая запись имеет UUID, сгенерированный на клиенте,
и метку `updatedAt`. Клиент шлёт изменённые записи и курсор `since`,
сервер отвечает всем, что изменилось после этого курсора.

Конфликты решаются правилом «последняя запись побеждает» по `updatedAt`.
Для дневника сна этого достаточно: два родителя редко правят одну запись
одновременно, а если правят — побеждает тот, кто сделал это позже.
Курсор `rev` — счётчик на стороне сервера, чтобы расхождение часов
на телефонах не ломало выборку.

Удаление мягкое: запись помечается `deleted` и уезжает на сервер, иначе
второй телефон воскресил бы её при следующей синхронизации. Помеченные
записи физически удаляются через 90 дней.

## Резервные копии

Вкладка «Неделя» → «Скачать резервную копию» (JSON).

На сервере всё лежит в `./data/tracker.db` (SQLite). Копировать так:

```bash
docker compose exec app sh -c 'sqlite3 /data/tracker.db ".backup /data/backup.db"' \
  || cp data/tracker.db data/backup-$(date +%F).db
```

## Если сервер не узнаёт ссылку

Если база на сервере пересоздалась (переустановка, потерянный том),
старый токен станет недействительным, а записи на телефоне останутся.
Приложение покажет кнопку «Перепривязать к серверу»: она заведёт дневник
заново с тем же профилем и зальёт туда всю локальную историю.

Старая ссылка для второго родителя после этого перестаёт работать —
отправьте новую из раздела «Неделя».

## Чего здесь нет

- **Уведомлений «пора спать».** Web Push на Android работает, но требует
  VAPID-ключей и планировщика на сервере. Если понадобится — это
  следующий шаг, либо обёртка в APK через Capacitor с локальными
  уведомлениями без сервера.
- **Нескольких детей.** Один дневник — один ребёнок.
- **Регистрации и паролей.** Доступ только по ссылке.
- **HTTP/3.** Приложение отдаётся по обычному TCP-соединению. Если рядом
  на 443 UDP работает что-то своё, оно живёт независимо и не мешает.

## Источники цифр

Суточная норма сна — консенсус AASM 2016 (J Clin Sleep Med 12(6):785),
поддержан AAP. Для детей младше 4 месяцев нормы нет намеренно: слишком
широкий разброс.

Окна бодрствования — сведённые открытые таблицы Huckleberry и Happiest
Baby. Это эвристика консультантов по сну, а не клинический норматив.
Правило выбора точки внутри окна (сдвиг к вечеру, поправка на короткий
предыдущий сон) — самодельное, это реконструкция логики, а не она сама.

Источники дают ступеньки по возрастным полосам. Значения закреплены за
серединами полос и между ними интерполируются линейно: ступенька — форма
подачи таблицы, а не факт о ребёнке, и на границе полосы окно прыгало
на 10-15 минут за одну ночь. Числа в узлах взяты из таблиц без изменений,
интерполяция между ними — наше соглашение.

Ночным считается сон, начатый до 05:00 (ночное пробуждение), либо
начатый вечером и длящийся от 2.5 часов или заходящий за 23:00. Только
по часу начала судить нельзя: короткий вечерний досып начинается в те же
часы, что и настоящий отбой, а после «ночного» сна прогноз берёт
минимальное окно.

До трёх месяцев поправка на время суток почти не применяется: устойчивый
циркадный ритм складывается к 6-12 неделям, суточная выработка мелатонина —
к 9-12, а до этого сон определяется голодом, а не внутренними часами.
В этом возрасте берётся середина возрастного диапазона, окно показывается
вдвое шире (±25 минут вместо ±12), и приложение объясняет почему.

Переход к расчёту по времени суток плавный, с весом от 0 на 2,5 месяцах
до 1 на 3,5. Жёсткий порог «ровно три месяца» давал разрыв до 40 минут
за одну ночь и вдвое сужал окно, хотя за эту ночь с ребёнком ничего
не происходит.

Позиция внутри дня определяется по времени суток, а не по числу
записанных снов: дневник почти всегда неполный (начали вести с обеда,
забыли отметить утренний сон), и счётчик записей в таких случаях даёт
слишком короткое окно. Точка отсчёта — конец записанного ночного сна,
а если его нет, берётся 07:00, и приложение честно пишет об этом.

## Давление сна и микросны

Состояние выражено явно: накопленное давление `P` в «минутах
бодрствования». Бодрствование копит его 1:1, сон рассеивает
экспоненциально — `P *= exp(−d/TAU)` при `TAU = 15` мин. Раньше любой
сон любой длины обнулял таймер целиком, и день после пары дремот
в автокресле рассыпался.

`TAU` — соглашение, полученное масштабированием, а не измеренная
у младенцев величина. У взрослых константа рассеивания Процесса S
≈ 2,4 ч при бодрствовании ~16 ч, отношение ≈ 6,7; при окне младенца
~110 мин то же отношение даёт ≈ 16 мин.

    5 мин  -> остаётся 72%     25 мин -> 19%
    10 мин -> 51%              50 мин -> 3,6%  (полный цикл)
    15 мин -> 37%              час и больше -> ~0

Ночной сон отдельной ветки не требует: при таком `TAU` формула сама
вырождается в прежнее «сон обнуляет всё».

Обратной поправки «необычно длинный сон -> окно позже» нет намеренно:
после любого полного сна давление и так рассеяно до нуля, источниками
она не подкреплена, а толкала окно позже — в ту сторону, где ошибка
сама себя воспроизводит.

Рядом живёт вторая поправка — «недоспал относительно своей нормы».
Это ДРУГОЕ явление: сон 55 мин при медиане 100 даёт переноса всего
3 минуты, хотя ребёнок явно недоспал. Складывать их нельзя (в области
очень коротких снов сработали бы дважды), поэтому берётся максимум.
Обе зависимости плавные, без ступенек на порогах.

Порог «короткого сна» относительный, а не абсолютный: берётся медиана
последних десяти дневных снов самого ребёнка. В 3-5 месяцев при
перестройке архитектуры сна почти все сны становятся односцикловыми
(30-40 минут), и фиксированный порог срабатывал бы на каждом, укорачивая
каждое окно ровно тогда, когда потребность в бодрствовании растёт.

Окно бодрствования делится на две фазы: активное бодрствование и
успокоение перед сном (10 минут до трёх месяцев, 15 до года, 20 дальше,
но не больше трети окна). Это соглашение, а не норматив — таблиц
для длительности подготовки ко сну не существует.

Личная поправка: насколько ребёнок засыпает позже или раньше середины
предсказанного окна. Берётся медиана последних десяти дневных засыпаний,
а не среднее — один сон, отмеченный с опозданием на полчаса (с младенцем
это норма), утягивал среднее за собой. Рядом считается разброс (MAD).

Поправка применяется автоматически, но не целиком. Доля растёт с числом
наблюдений как n/(n+3) — при пяти снах берётся 63%, при десяти 77%,
полностью не берётся никогда: дневник в два-три дня легко поймать
на нетипичном дне. Если разброс сопоставим с самой поправкой, доля
дополнительно снижается — это шум, а не систематический сдвиг. Поправка
меньше пяти минут игнорируется, это уровень округления ручной отметки.
Ручной сдвиг ±5 минут добавляется сверх автоматической.

Измеренный разброс засыпаний расширяет и само окно (до +15 минут):
если ребёнок ложится вразброс, узкое окно — ложная точность.

Стороны поправки неравноправны. Отрицательная («ребёнок готов раньше»)
берётся целиком: ошибиться рано дёшево, ребёнок не уснул — попробовали
через четверть часа. Положительная берётся вполовину, потому что она
сама себя воспроизводит: приложение сдвигает окно позже, родители кладут
позже, приложение измеряет собственный сдвиг как факт о ребёнке.
В симуляции с родителями, которые кладут с постоянным опозданием, окно
без защиты уезжало на 44 минуты позже реальной готовности за 28 дней
и продолжало расти.

## Метки укладывания

Записанное время засыпания — это момент, когда РОДИТЕЛЯМ удалось
уложить, а не момент, когда ребёнок был готов. По одному наблюдению эти
две величины неразличимы в принципе, поэтому нужна метка от родителя.

Меток две, и ставятся они ТОЛЬКО когда есть что отметить. Обычное
укладывание метки не требует — отсутствие метки означает «ничего
особенного» и идёт в измерение как есть.

- «плакал» — положили ПОЗДНО, окно упущено. Засыпание позже прогноза
  ничего не доказывает и отбрасывается; раньше прогноза — учитывается.
- «был бодрый» — положили РАНО, ребёнок ещё не готов. Момент засыпания
  и есть его настоящая готовность, самое информативное наблюдение
  из всех. Не отбрасывается ничего.

Разделение этих двух получено дорогой ценой. Сначала обе ситуации лежали
на одной кнопке «долго не мог», и приложение всегда читало её как
«опоздали». При настоящем сбросе сна происходит обратное — ребёнку нужно
окно ДЛИННЕЕ, — и все три защиты складывались в одну неверную сторону:
measureBias выбрасывал все такие наблюдения и возвращал null,
settleNudge тянул окно раньше, autoBias гасил поправку в ноль.
В симуляции сброса сна приложение с метками отставало от истинного окна
на 88 минут против 24 БЕЗ меток вообще, то есть метки делали хуже.

Были ещё две нейтральные метки, «уснул сразу» и «повозился». Убраны:
на прогонах четырёх сценариев они не давали ничего (разница в пределах
минуты), а требовали отмечать каждый сон. Хуже того, «уснул сразу»
сначала выбрасывался из измерения целиком — ошибка отбора, при которой
выбрасывались ровно те укладывания, где всё прошло хорошо (28% всех
наблюдений), а поправка мерилась по одному хвосту. На прогоне
нормального сценария с ВЕРНОЙ моделью это завышало оценку на 5-27 мин.

Знаменатель долей — ВСЕ дневные сны за неделю, а не только размеченные.
Это принципиально: если считать по размеченным, то родитель, отмечающий
лишь проблемные укладывания (единственное человеческое поведение),
получает долю ровно 1.0. Четыре плохих сна из двадцати дают ноль, пятый
— сразу −30 минут. По всем снам те же пять дают −8, и зависимость
плавная.

Сдвиг по меткам ОДНОСТОРОННИЙ, только от «плакал»:

    сдвиг = −30 × доля«плакал»

Асимметрия — следствие того, что measureBias делает с каждой меткой.
Наблюдения «плакал» он отбрасывает, поэтому сигнал «положили поздно»
больше проходить некуда и сдвиг ему единственный канал. Наблюдения
«был бодрый» он учитывает полностью, и растянутое окно уже отражается
в поправке — свой сдвиг сверху был бы тем же сигналом, посчитанным
дважды. На прогонах двусторонний вариант проигрывал одностороннему:
норма +9 против −1, сброс сна +9 против −4.

Поэтому «был бодрый» влияет только на множитель доверия: он ничего
не измеряет заново, а разрешает применить уже измеренное целиком.

Положительная поправка проходит через множитель доверия:

    trust = clamp01(0,5 + 0,5·доля«был бодрый» − доля«плакал»)

Без меток это 0,5. Сплошь «плакал» — ноль. Сплошь «был бодрый» —
единица: прямое свидетельство, что клали рано.

База 0,5 — это защита именно для тех, кто не размечает вовсе. Прогон
с доверием 1,0 и без метки «был бодрый» отлично держал сброс сна, но
в сценарии «родители систематически опаздывают и ничего не отмечают»
давал отклонение +93 минуты: петля обратной связи возвращалась целиком.

Это регулятор, а не накопитель: сдвиг считается заново от текущих долей,
окно уезжает в нужную сторону, укладывания даются легче, доли падают,
сдвиг уходит сам.

## Версия локального состояния и миграция

`store.js` хранит `schema` в состоянии устройства. Версия поднимается,
когда меняется СМЫСЛ уже сохранённого поля, а не только набор полей —
тогда старое значение надо не дополнить, а обезвредить.

Версия 2: `bias` сменил смысл. Раньше кнопка «Применить измеренную
поправку» записывала туда ВСЮ поправку целиком (скажем, 36 минут).
Теперь приложение считает поправку само, а `bias` — ручная добавка
ПОВЕРХ неё. Старое значение стало бы вторым слагаемым того же самого:
тихое удвоение, о котором никто бы не догадался. Вдобавок шагом ±5
из 36 в ноль не попасть, то есть руками это было не убрать.

При загрузке состояния со `schema < 2` ручная поправка обнуляется,
а снятое значение запоминается в `biasResetFrom` и один раз
показывается на вкладке «Неделя». Миграция идемпотентна и не трогает
остальные поля.

Ручная добавка ограничена `MANUAL_BIAS_LIMIT = 30` минут: она
единственная величина, идущая в кламп мимо всего демпфирования.

## Склейка фрагментированного сна

Ночь, прерванная кормлением, записывается как два-три события. По часам
хвост ночи (подъём в 5:30, сон с 6:05 до 7:20) попадал в «день» и
считался первым дневным сном. Из-за этого `typicalNap` видел короткие
обрывки вместо нормальных снов, `measureBias` строил лишнее наблюдение
с окном бодрствования в двадцать минут, а «снов днём» завышалось.

Так это и делают в актиграфии: ночь определяют как интервал от
засыпания до утреннего подъёма, а пробуждения внутри считают WASO —
временем бодрствования ВНУТРИ периода, а не его концом. Ночной интервал
при этом опознают по обычному времени отхода ко сну, то есть окна
активности дополняют часы, а не заменяют их.

Два шага: сначала склейка соседних снов с коротким промежутком в один
период, потом обычная классификация склеенного по часам и длительности.

Порог зависит от времени суток, и это существенно:

- днём — половина минимального возрастного окна (33 мин в 3 месяца,
  55 в полгода): промежуток проверяется на «тянет ли он на окно
  бодрствования»;
- ночью, с 22:00 до 07:00 — фиксированные 60 минут. Ночью понятия окна
  бодрствования нет вообще, ребёнок не должен бодрствовать, а кормление
  с переодеванием занимает 30-50 минут. Возрастная доля дала бы
  33 минуты, и обычное ночное кормление рвало бы ночь надвое.

Склейка применяется там, где приложение учится и классифицирует.
`carryOver` работает по сырым записям: за двадцать минут бодрствования
давление действительно частично восстановилось, и рекурсивная формула
это уже учитывает. Показ на вкладках тоже сырой — родитель записал два
события и должен видеть два.

## Форма дня: наклон поправки

Одна общая поправка умеет только сдвинуть весь день целиком. Если
у ребёнка форма дня не та, что предполагает таблица — окна одинаковые
весь день или растут круче, — ошибка систематически едет от утра
к вечеру, и скаляр её не берёт. На прогонах размах между первым
и последним сном доходил до 46 минут.

Поправка поэтому может быть не числом, а парой «утро/вечер»: медианы
расхождения по половинам дня, между которыми интерполируется по
прогрессу. Значения относятся примерно к прогрессу 0,25 и 0,75, за
краями держится ровно — экстраполировать наклон, измеренный по двум
точкам, было бы самонадеянно. Раздельные половины применяются, только
если в каждой хватает наблюдений И расхождение больше шума.

ЧИНИТСЯ ИМЕННО НАКЛОН, А НЕ ПОДСТРОЙКА ПОД НОМЕР СНА. Номер сна —
координата ненадёжная: дневник почти всегда неполный, забыли отметить
утренний сон, и все подстройки поехали на слот. Плюс при сбросе сна
номера перенумеровываются, и всё выученное про «четвёртый сон»
обессмысливается ровно тогда, когда ребёнок меняется сильнее всего.
Прогресс дня по часам к пропускам устойчив, и по нему уже считается
вся остальная модель.

Выигрыш честно скромный: размах ошибки по дню сузился примерно на
четверть (у «плоского» ребёнка с 36 до 26 минут, у «крутого» с 46 до
35). Больше не выходит, потому что положительную сторону поправки
режет защита от петли обратной связи, а она нужнее.

## Самопроверка против голой таблицы

Приложение проверяет само себя: для последних засыпаний строит два
прогноза по данным ДО каждого — со всеми поправками и по голой
возрастной таблице — и сравнивает медианы абсолютной ошибки. Если
таблица выигрывает с запасом в 5 минут, поправки временно отключаются,
и на вкладке «Неделя» об этом написано. Ручной сдвиг родителя при этом
сохраняется.

Оговорка о честности сравнения важнее самого механизма. История не
независима от модели: родители укладывали ребёнка по тому прогнозу,
который им показывали, поэтому засыпания подтянуты к применённому
варианту. Тест СМЕЩЁН В ПОЛЬЗУ поправок. Именно поэтому обратный
результат — когда голая таблица всё равно точнее — сильное
свидетельство, а не шум: поправки проиграли, имея фору.

Выключатель, а не сброс: `autoBias` и `settleNudge` не накапливаются
в состоянии, а считаются заново от истории при каждом вызове. Сбрасывать
там нечего — можно только перестать применять, и это самоисцеляется,
когда данные меняются.

Самопроверка кэшируется по дешёвой подписи входа: внутри неё
measureBias вызывается в цикле, работа квадратичная. Без кэша выходило
48 мс на вызов против 2,3 мс у остального прогноза — и это на каждый тик
часов раз в 15 секунд. С кэшем 48 мс платятся один раз при изменении
данных, дальше 2,3 мс.

Ни в одном из проверенных сценариев выключатель не сработал, включая
специально отравленную историю (неделя записей с опозданием на 70 мин).
Это хорошая новость про алгоритм, но означает, что в поле он непроверен.
Сам путь отключения проверен принудительно, через заниженный порог:
обе поправки обнуляются, ручной сдвиг остаётся.

## Разделы и вкладки

Навигация двухуровневая. Наверху два раздела, внизу — вкладки того
раздела, который выбран:

- **Сон** — «Сейчас», «День», «Неделя»;
- **Здоровье** — «Вес», «Рост», «Голова».

Разделение не косметическое: «Сон» открывают по несколько раз в день,
«Здоровье» — раз в неделю. В одном ряду часто нажимаемое
соседствовало бы с редким. При переключении раздела всегда
открывается его первая вкладка, иначе экран остался бы от прошлого
раздела, а нижние кнопки показывали бы не то, что открыто.

Вторая вкладка раздела «Сон» называется «День», а не «Сегодня»:
она листается стрелками на любую прошлую дату.

## Раздел «Здоровье»: вес, длина, окружность головы

Три вкладки на одном коде: `MeasureView` и `GrowthChart` принимают
описание показателя (`IND` в `web/src/growth.js`), где лежат таблица,
единицы, шаг сетки, шаг кнопок и цвет. Различается только это.

Данные — WHO Child Growth Standards (2006), таблицы L/M/S:
понедельные до 13 недель и помесячные дальше, отдельно для мальчиков
и девочек. Вес и окружность головы — до 5 лет, длина — до 2 лет:
после двух лет ВОЗ измеряет рост стоя, а это другая величина
(примерно на 0.7 см меньше), и склеивать их одной кривой нельзя.

У длины и окружности головы ВОЗ полагает L = 1 на всех возрастах:
распределение нормальное, и формула вырождается в M + z·M·S. Код
этого не знает и считает общим случаем — одна ветка вместо двух,
результат тот же.

Значения хранятся целыми во внутренних единицах: вес в граммах
(`meta.g`), длина и голова в миллиметрах (`meta.mm`). Ключ задаётся
в `IND[...].metaKey`; у веса он остался прежним, чтобы уже
записанные взвешивания читались без миграции.

**Про точность домашних измерений.** Для веса это оговорка, для
длины и головы — предупреждение по существу. Разброс длины
у трёхмесячных около 2 см на одну z-оценку, а ошибка измерения лентой
на извивающемся ребёнке легко достигает того же сантиметра: половина
«изменения перцентиля» может оказаться тем, как в этот раз легли
ноги. У головы разброс около 1.2 см на z, а расхождение между двумя
обмерами подряд бывает в полсантиметра. Это сказано в интерфейсе
прямо, вместе с техникой измерения.

**Направление тревоги** задаётся полем `alarm`. У веса и длины она
срабатывает только на смещение вниз. У окружности головы — в обе
стороны (`"both"`): быстрый уход вверх здесь значим не меньше, и это
то, за чем следят на приёмах. Формулировка от этого не становится
тревожнее: порог тот же (1.0 z, не раньше чем через 14 дней),
приложение по-прежнему ничего не утверждает и отправляет к педиатру.

Типы событий `weight`, `length` и `head` внесены в белый список
в `server/index.js` — неизвестные типы там молча падают в `feed`.

Перцентиль считается формулой, а не берётся из округлённой таблицы:

    z = ((значение / M)^L − 1) / (L·S)   (при L = 0 — log(значение/M)/S)

Между узлами L, M и S интерполируются линейно по дням. Транскрипция
таблиц проверена обратным счётом: из зашитых L/M/S пересчитаны все
колонки −3…+3 SD по всем трём показателям и сличены с опубликованными
ВОЗ — **791 значение, расхождений сверх округления до 0.1 нет**.

Решения, которые стоит знать, прежде чем менять:

- **Рисуются линии z-оценок, а не перцентильные кривые.** Считаем мы
  z; рисовать одно, а считать другое — способ разойтись на
  округлениях. Перцентиль показывается числом рядом с графиком.
- **Темп прибавки считается только по плечу от 7 дней**
  (`GAIN_MIN_DAYS`). Домашние весы врут на ±20–50 г, полный подгузник —
  на 200. На плече в два дня погрешность больше самой прибавки.
- **Ориентир прибавки — разность медиан ВОЗ, а не стандарт скорости.**
  У ВОЗ есть отдельные таблицы weight velocity, они считаются иначе и
  по коротким отрезкам шире. В интерфейсе это оговорено текстом.
- **Одна тревожная формулировка, мягкая.** Порог — падение z на 1.0 от
  собственного максимума ребёнка (`Z_DROP_ALARM`), не раньше чем через
  14 дней после этого максимума. Это консенсусное определение
  faltering growth; NICE NG75 формулирует то же через «полосы»
  британских кривых, они шире на 2/3 z.
- **Первые три недели исключены из тренда.** Физиологическая убыль
  веса (до 7–10 % от веса при рождении, возврат к 10–14 дню) по
  z-оценке выглядит как обвал на целую единицу и была бы принята за
  тревогу.
- **Скорректированный возраст для недоношенных не считается.**
  Стандарт построен на доношенных детях; для родившегося раньше срока
  перцентиль будет занижен. Оговорено в интерфейсе.

Вес хранится в **граммах целым числом** (`meta.g`): дробные килограммы
в JSON дают `6.300000000000001`.

Пол ребёнка живёт в профиле (`households.sex`, миграция через
`ALTER TABLE`). На сервере он пишется через `COALESCE(@sex, sex)`:
телефон со старой версией приложения присылает профиль без этого поля
и иначе обнулил бы уже выбранный пол при первой же синхронизации.

Тип события `weight` добавлен в белый список типов **одновременно** в
`server/index.js` и на клиенте: неизвестные типы там молча падают
в `feed`.


## Кормления: когда можно кормить

Отдельный расчёт (`web/src/feed.js`), который отвечает НЕ на вопрос
«голоден ли ребёнок», а на вопрос «освободился ли желудок». Это
разные вещи, и путать их нельзя: приложение видит момент кормления,
а не момент, когда ребёнок захотел есть, — ровно та же разница, что
между «уснул» и «был готов уснуть». Поэтому все формулировки
разрешительные («можно кормить»), а не повелительные («пора»), и
кормление по требованию расчёт не заменяет.

Как считается:

1. **Опорожнение желудка** — экспоненциальное, период полувыведения
   47 мин для грудного молока и 65 мин для смеси (дыхательный тест
   с 13C-октановой кислотой у доношенных). Разброс в исходной работе
   16–86 и 27–98 минут, поэтому модель даёт порядок величины.
2. **Объём кормления.** Для смеси — введённый руками. Для груди его
   никто не измеряет, и это главная слабость: он выводится из
   суточного объёма (мл/кг/сут по возрасту × вес из вкладки «Вес»),
   делённого на СОБСТВЕННУЮ медиану числа кормлений за сутки.
   Мета-анализ 167 исследований: 135 мл/кг/сут в 1 мес, 126 в 3 мес,
   107 в 6 мес, 61 в 12 — в абсолюте 624 / 735 / 729 / 593 мл.
3. **Полнота дневника.** Пропуск сам по себе неинформативен, но
   промежуток, закрытый отмеченным СНОМ, — настоящий: ребёнок точно
   не ел. Отсюда `sleepCoverage`. Длинный промежуток без сна и без
   записей считается дыркой в дневнике, и напоминание подавляется.
4. **Короткая память.** Через 3 периода полувыведения остаётся ~12 %,
   через 4 — ~6 %. Состояние «до пропуска» забывается за 2.5–3 часа,
   поэтому одного отмеченного кормления хватает, чтобы расчёт снова
   стал осмысленным. На симуляции шестичасовая дырка в дневнике сдвинула
   момент «можно кормить» на 15 минут, а время напоминания — на ноль.

`readyAt` — когда в желудке останется меньше `READY_FRACTION` (0.25)
типичного объёма. `dueAt` — момент напоминания: не раньше `readyAt`
и не раньше, чем пройдёт собственный медианный промежуток между
кормлениями, иначе пуш приходил бы каждые полтора часа.

Напоминание не отправляется, если ребёнок спит, если момент попадает
на ночь (07:00–22:00 — окно `DAY_FROM_HOUR`/`DAY_TO_HOUR`), если
дневник выглядит неполным или если момент прошёл больше часа назад.
Если окно кормления открывается в пределах 20 минут от начала фазы
успокоения, остаётся только напоминание о сне: у него есть срок
годности, а покормить можно и позже.

**Обучения на собственных подсказках здесь нет намеренно.** Все
параметры — физиологические константы; единственное личное число
(медиана числа кормлений) берётся из фактических записей. Иначе
возникла бы та же петля обратной связи, что и с окнами сна.

Прикорм и вода в модель не входят: вода уходит быстро, твёрдая пища
заметно тормозит опорожнение, и то и другое требует своих констант.
После введения прикорма расчёт станет заметно хуже — это надо будет
чинить, а не игнорировать.

## Очередь уведомлений

Колонки `notify_*` в `households` заменены таблицей `notifications`
с ключом `(household_id, kind)`. Видов стало больше одного, и на
каждый новый пришлось бы добавлять четыре колонки и ветку
в планировщике. **Текст сообщения готовит клиент** — там же, где
считается прогноз, — поэтому новый вид уведомления вообще не требует
правок на сервере.

Старые колонки не удаляются (SQLite не везде умеет `DROP COLUMN`,
а пустые колонки не мешают). Единственное следствие обновления:
уведомление, стоявшее в очереди по старой схеме в момент деплоя,
не отправится. Клиент пересчитает и поставит его заново при
ближайшей синхронизации, то есть в пределах полуминуты.

`/api/sync` принимает **обе** формы поля `notify`: новую
`{ sleep: {...}|null, feed: {...}|null }` и старую
`{ at, fromLabel, toLabel }`. Без поддержки старой формы на телефоне,
где приложение ещё не обновилось, напоминания о сне молча перестали
бы приходить.

Выбор видов уведомлений хранится в `households.notify_off` — списком
ОТКЛЮЧЁННЫХ через запятую. Именно отключённых, а не включённых:
тогда вид, добавленный в будущей версии, у существующих семей
заработает сам, а не окажется молча выключенным. Настройка едет
через профиль тем же LWW-механизмом, что имя и дата рождения, и
пишется через `COALESCE`, чтобы старый телефон её не обнулил.
Настройка общая на семью; раздельная на каждого родителя требовала бы
привязки к `chat_id` — это отдельная задача.

## Ночной сон: склейка и ручная пометка

`isNightSleep` смотрит на одну запись и на час её начала. Для прогноза
этого хватает, потому что прогноз работает со СКЛЕЕННЫМИ блоками
(`mergeSleeps`). А список записей, счётчики дня и недельные медианы
работали с сырыми событиями — и ломались:

    02:28–05:17  ночной сон
    05:19        кормление
    05:45–06:36  «дневной сон» — та же ночь, ребёнок поел и лёг обратно

51 минута ночного сна засчитывалась дневной, счётчик «снов днём» врал
на единицу, недельная медиана дневного сна получала наблюдение,
дневным сном не являющееся.

Различает эти случаи не час, а НЕПРЕРЫВНОСТЬ. Ровно это считает
склейка, поэтому `nightFragments(events, birth, now)` спрашивает у неё:
в какой блок попала запись и ночной ли этот блок. Незакрытый сон
склейка отбрасывает, поэтому для классификации он временно
закрывается текущим моментом.

Прогноз от этой правки не изменился (проверено на реальном дне:
07:35–08:07 до и после), менялись только подписи и счётчики.

**Ручная пометка сильнее автоматики.** В карточке правки сна три
кнопки: «Дневной», «Ночной», «Авто». Родитель один знает, было ли
между снами настоящее бодрствование. Пометка `meta.night` не только
меняет подпись, но и РАЗРЫВАЕТ СКЛЕЙКУ: сон, помеченный дневным,
не приклеивается к ночному блоку и считается отдельным окном
бодрствования.

Известный компромисс, оставленный сознательно: порог склейки в ночные
часы — 60 минут, а «ночные часы» тянутся до 07:00. Подъём в 06:00,
час бодрствования и сон в 06:50 склеятся в ночь, хотя это уже
настоящий утренний сон. Теперь это лечится пометкой вручную.

## Доверие к поправке без меток укладывания

`autoBias` применяет положительную поправку через множитель доверия.
Раньше базой при ОТСУТСТВИИ меток стояло 0,5 — половина измеренной
поправки молча выбрасывалась не за плохие метки, а за их отсутствие.

На реальной истории это оказалось ошибкой. 11 дневных снов, все
одиннадцать наблюдений положительные, медиана +31 при разбросе ±11:
приложение применяло +12 и промахивалось систематически на +21
минуту — медианное засыпание лежало ЗА верхней границей выдаваемого
окна. Смещение и разброс — разные величины: систематическую ошибку
надо СДВИГАТЬ, а не расширять границы.

Walk-forward по этой истории (поправка считается только по данным
до каждого сна, 7 оценочных точек после разогрева):

| вариант | попаданий | медиана \|ошибки\| | медиана сдвига |
|---|---|---|---|
| база 0,5 (было) | 4/7 | 21 мин | +21 мин |
| база 0,85 (стало) | 4/7 | 13 мин | +13 мин |
| без множителя вовсе | 5/7 | 17 мин | +1 мин |

Отказ от штрафа за отсутствие меток безопасен потому, что тормоз уже
есть и он ИЗМЕРЯЕТ, а не предполагает: `selfCheck` сравнивает поправку
с голой таблицей на собственной истории ребёнка и выключает её, если
та проигрывает (на тех же данных: 22 минуты ошибки против 34 у
таблицы). Множитель 0,5 при нулевых метках тормозил второй раз вслепую.

Взято 0,85, а не 1,0: данных было четыре дня и семь оценочных точек —
достаточно, чтобы увидеть направление, мало, чтобы утверждать величину.
`HARD_PENALTY` = 1,7 подобран так, чтобы доля «плакал» в 0,5
по-прежнему обнуляла поправку целиком: сдвинута только точка
«свидетельств нет», тормоз по плачу прежней силы. Отрицательная
поправка, как и раньше, идёт целиком без множителя.

Отдельно стоит помнить, ПОЧЕМУ поправка вообще так велика: у ребёнка
из этой истории фактические окна бодрствования 90–168 минут при
медиане 121, а таблица для его возраста даёт 69–117. Таблица ему
не подходит, и поправка компенсирует именно это.

## Дубли уведомлений

Время напоминания зависит от возраста в месяцах, то есть от текущего
момента непрерывно: между синхронизациями расчёт уезжал на секунды,
сервер видел «другое» время, перевзводил уведомление со снятым флагом
отправки — и сообщение уходило второй раз с теми же границами окна.

Чинится с двух сторон: клиент округляет время до минуты
(`toMinute` в `store.js`), сервер не перевзводит уже отправленное
уведомление, если новое время ближе `RE_ARM_GAP_MS` (20 минут) к
старому. Настоящий сдвиг окна взводит напоминание заново, как и
раньше.

## Собственное окно бодрствования: прямая вместо числа

`autoBias` умеет двигать предсказание целиком, но не умеет менять его
НАКЛОН. На реальной истории оказалось, что таблица промахивается
именно наклоном: предсказывала окна 74–100 мин (размах 26) там, где
фактические были 90–168 (размах 79) — втрое уже реальности. Утром
модель предсказывает поздно, вечером рано, и обе ошибки ложатся
в разброс, которым потом расширяется окно.

Хуже того, расширение как компенсация не работает в принципе.
Разброс — это MAD, а **MAD не меняется от сдвига**: сколько поправку
ни применяй, ширина не сузится ни на минуту. Проверено в лоб: MAD 16
до сдвига на всю медиану и MAD 16 после. Ширина и центр были
развязаны, и ширина просто фиксировала долг модели.

`personalWindow(events, birth, now)` подгоняет по собственным дневным
снам прямую `окно = a + b·прогресс_дня` методом наименьших квадратов
и даёт `lo = a`, `hi = a + b` вместо табличных. Тогда центр целится
формой, а не сдвигом, — и `measureBias` начинает мерить ОСТАТКИ
относительно личной прямой, поэтому ширина впервые начинает сужаться
по мере того, как модель становится точнее.

Подгонка идёт по `окно + вычет`, а не по голому окну: `carryOver` и
штраф за короткий сон вычитаются из target позже, и без возврата
вычета прямая впитала бы их и применила дважды.

Прямая не заменяет таблицу разом, а подмешивается с весом
`n/(n+FIT_SHRINK)` — тот же приём усадки, что и в `autoBias`.
При 6 снах треть, при 12 половина, при 40 три четверти. Полностью
таблица не отбрасывается никогда. Результат зажат в 30–300 мин по
нижней границе и 360 по верхней: подгонка по десятку точек может
дать что угодно, включая отрицательный наклон.

Проверка на 21 дне синтетики, где окно = 100 + 60·прогресс ± 8 мин
(таблица для возраста даёт 69–117):

| | попаданий | медиана \|ошибки\| | смещение | измеренный разброс |
|---|---|---|---|---|
| было | 30/35 | 17 мин | +17 мин | ±11 мин |
| стало | 32/35 | **7 мин** | **+2 мин** | **±9 мин** |

Контроль на ребёнке, которому таблица ПОДХОДИТ (69 + 48·прогресс):
7 → 5 мин, ухудшения нет.

На реальной истории Василисы прирост скромнее (попаданий 4/11 → 5/11,
смещение +22 → +18), потому что при четырёх днях дневника вес прямой
меньше половины. Это не осторожность ради осторожности: подогнать
прямую по одиннадцати точкам и поверить ей — верный способ выучить
нетипичную неделю.

Отключается прямая вместе со всей обученной частью: `selfCheck`
сравнивает полную модель с ГОЛОЙ таблицей (`predictWindow(...,
{ personal: false })`), и при провале `predictNext` снимает и поправку,
и прямую — иначе «выключено» означало бы только половину.

## Ширина окна — константа

Раньше полуширина складывалась из возрастной добавки и измеренного
разброса засыпаний: `half = 25 + (12−25)·cw + min(spread/2, 15)`.
Это была ошибка замысла. Окно расширялось ровно там, где модель хуже
предсказывает, то есть промах не компенсировался, а прятался.

Не компенсировался он и арифметически: разброс считается через MAD,
а **MAD не меняется от сдвига** — сколько поправку ни применяй, ширина
не сузится ни на минуту. Ширина и центр были развязаны, и ширина молча
фиксировала долг модели вместо того, чтобы этот долг был виден.

Теперь `half = WINDOW_HALF` (15 минут, окно 30). Попасть в окно —
задача алгоритма, а не границ. Параметр `spread` из `predictWindow`
убран совсем, чтобы не оставлять мёртвой ручки.

Цена решения известна и её надо знать. На реальной истории:

| | попаданий | медианный промах | средняя ширина |
|---|---|---|---|
| ширина по разбросу | 6/12 (50 %) | 19 мин | 39 мин |
| ширина постоянная | 5/12 (42 %) | 19 мин | 31 мин |

Медианный промах не изменился — он и не мог измениться, ширина на
центр не влияет. Изменилось только то, что промах перестал быть
замаскированным.

Ширина одна и та же во ВСЕХ источниках: `half = WINDOW_HALF` стоит в
`predictWindow` без единого ветвления. Это не косметика — без неё
сравнивать источники было бы нельзя в принципе: тот, кому досталось
окно шире, выигрывает шириной, а не точностью.

## Четыре источника прогноза и выбор между ними

Приложение считает прогноз четырьмя способами и берёт тот, что
промахивался меньше на последних `PICK_TAIL` (10) дневных снах:

| источник | что это |
|---|---|
| **Алгоритм** | личная прямая + поправка + перенос давления |
| **Своя таблица** | `WINDOW_ANCHORS`, усреднённая по источникам |
| **Taking Cara Babies** | опубликованная таблица, без правок |
| **Huckleberry** | опубликованная таблица, без правок |

Чужие таблицы взяты как опубликованы — без усреднения, сглаживания и
подгонки. Смысл в том, что «наша таблица лучше» перестаёт быть
допущением: если чужая на этом ребёнке точнее, работает она.

**Taking Cara Babies:** 0–4 нед 30–60 мин, 4–12 нед 60–90,
3–4 мес 75–120, 5–7 мес 2–3 ч, 7–10 мес 2.5–3.5 ч, 11–14 мес 3–4 ч,
14–24 мес 4–6 ч. Узлы поставлены в середины возрастных диапазонов,
потому что таблица задана диапазонами возраста, а не точками.

**Huckleberry:** новорождённые 30–90 мин, 3 мес 60–120, 4 мес 90–150,
6 мес 2–3 ч, 12 мес 3.25–4 ч, 24 мес 5.5–6 ч.

`sourceScores` считает всё walk-forward: для каждого сна каждый
источник строит прогноз только по данным до него. `pickSource`
выбирает наименьший медианный промах, но **алгоритм держит фору
`PICK_MARGIN` (4 минуты)**: он единственный, кто учится на этом
ребёнке, и менять его на статичную таблицу из-за минутного перевеса
на десяти наблюдениях значило бы выучить шум.

Выбор без памяти, чисто по цифрам: одни и те же данные всегда дают
один и тот же ответ. Это сознательно — состояние здесь означало бы
скрытую зависимость от порядка, в котором приложение открывали.

На реальной истории (12 дневных снов):

| источник | попаданий | медианный промах |
|---|---|---|
| Алгоритм | 3/10 | **20 мин** |
| Своя таблица | 1/10 | 33 мин |
| Taking Cara Babies | 1/10 | 32 мин |
| Huckleberry | 2/10 | 29 мин |

Все четыре показываются в «Неделе» карточкой «Точность прогноза»,
выбранный отмечен. `hitRate()` удалена — `sourceScores()` делает то же
самое для всех источников сразу.

## Ввод кормлений: бутылочка и грудь по таймеру

**Бутылочка** — кнопка, за ней выбор «Смесь / Молоко / Вода» и объём.
`ebm` (сцеженное грудное молоко) — отдельный вид, а не смесь: объём
у него известен точно, но опорожняется он как грудное молоко, 47 минут
против 65 у смеси. Вода в модель наполнения не входит.

**Грудь** — кнопка-таймер, вторым нажатием закрывает кормление.
Незакрытое кормление — то же соглашение, что у сна: `end === null`
означает «идёт сейчас». Длительность кладётся в `meta.sec`, а не
выводится из `end − start`: запись потом можно подвинуть по времени,
и длительность от этого меняться не должна.

Старые виды `left` / `right` остаются читаемыми ради истории, но
новых записей такого рода больше не создаётся: отметка без времени
давала объём «по умолчанию» для любого кормления, от двухминутного
до получасового.

### Пересчёт минут в миллилитры

Молоко уходит не равномерно — основная часть передаётся в первые
минуты. Форма кривой насыщающая: `V(t) = V·(1 − exp(−t/τ))`,
`LETDOWN_TAU = 4` мин. Проверка формы: к 10.5 минутам — средней
длительности кормления в исследовании с контрольным взвешиванием
доношенных — передаётся 93 %.

Из литературы взята **только форма**. Масштаб — собственный: в том же
исследовании при средних 119.5 г на кормление разброс был 34–222 г,
шестикратный, и абсолютные миллилитры оттуда брать бессмысленно.
Кривая нормируется на СВОЮ медианную длительность (`typicalFeedMinutes`),
так что кормление типичной длины даёт ровно типичный объём:

    типичный объём 105 мл, своя медиана 12 мин
     2 мин ->  43 мл      10 мин -> 101 мл
     4 мин ->  70 мл      12 мин -> 105 мл
     6 мин ->  86 мл      20 мин -> 110 мл

Кривая насыщается: держать ребёнка у груди вдвое дольше не значит
влить вдвое больше, и оценка это отражает.

### Число кормлений в сутки

Считается медиана только по ПОЛНЫМ дням: тем, где есть кормление
и до 9 утра, и после 19 вечера (`isFullDay`). Считать по числу
записей нельзя — тогда «мало кормлений» и «мало отмечено»
неразличимы, а неполные дни занижают медиану и тем ЗАВЫШАЮТ
оценку порции (суточный бюджет делится на меньшее число).

Родитель может задать число вручную кнопками ±1 в карточке
«Кормления»: значение живёт в `state.feedsPerDay` (null — считать
самим) и идёт во все расчёты, включая уведомления.

## Три исправленных бага

**Статистика источников не обновлялась.** В `sourceScores` цикл шёл
ВПЕРЁД от начала истории и обрывался по счётчику `n >= tail`, то есть
брал ПЕРВЫЕ десять дневных снов, а не последние. Числа переставали
меняться навсегда, сколько бы новых снов ни добавлялось. Теперь
индексы собираются с конца и разворачиваются. На реальной истории
статистика сразу поехала: алгоритм 3/10 (20 мин) → 5/10 (16 мин).

**Уведомление приходило после того, как прогноз устарел.** Клиент
пересчитывает расписание только когда работает, а телефон ночью
выключен — сервер отправлял то, что поставили час назад, даже если
ребёнка успели покормить. Проверка обязана быть на сервере.

Уведомление теперь несёт охранные поля `guard_type` / `guard_after`:
на какой момент дневника оно рассчитано. Перед отправкой сервер
считает `newerEventSince` — есть ли записи этого типа с
`updated_at > guard_after`. Есть — отправка отменяется. Ловятся и
новые записи, и правки задним числом: у правки тоже растёт
`updated_at`, а исправленное кормление меняет прогноз ровно так же,
как только что случившееся. Колонки добавляются миграцией через
`ALTER TABLE`.

**Таймер груди нечем было остановить.** Воспроизвести в браузерном
тесте не удалось — кнопка закрывалась исправно, — поэтому исправлено
структурно: отдельная крупная кнопка «Закончить кормление» вместо
переключателя, закрытие ВСЕХ незакрытых кормлений разом (если по
любой причине открылось несколько, одна кнопка закрывает все), и
запрет заводить второе открытое кормление.

## Пять правок по заявкам

### 1. Длительность кормления грудью редактируется

В карточке правки события с `meta.kind === "breast"` — поле
«Длительность» с шагом ±1 минута, меняет `meta.sec` напрямую. Объём
пересчитывается по новой длительности независимо от того, когда
кормление началось и закончилось: длительность и время — разные поля,
как и было задумано изначально.

### 2. Устаревшие пуши — найден и исправлен настоящий баг

`putNotify` на сервере: когда клиент присылал `notify.feed`/`notify.sleep`
с временем, которое уже считается невалидным (прогноз протух, момент
в прошлом больше чем на 5 минут), функция раньше делала `return`
**не трогая старую запись в очереди**. Именно так уходили неактуальные
пуши: протухание не переносилось на сервер, потому что сервер узнавал
о нём только через «новое валидное время», а протухание — это
ОТСУТСТВИЕ валидного времени. Теперь в этой ветке невыполненная
(`sent = 0`) запись снимается.

Структурно уведомление всегда одно на вид (`PRIMARY KEY (household_id,
kind)`, `ON CONFLICT DO UPDATE`) — это уже гарантировало «только один
пуш в очереди», проблема была именно в том, что устаревший расчёт не
приводил к снятию.

Проверено: поставленный будущий пуш, затем пересчёт с просроченным
временем — запись пропадает; явный `null` (ребёнок уснул) — тоже
пропадает.

### 3. Сумма еды на недельном графике

`dayFeedMl(events, dayStart, typicalMl, refMin)` в feed.js — оценка
объёма за сутки той же моделью, что и на вкладке «Сейчас» (точный
объём для смеси/сцеженного молока, по длительности для груди). Вода
и прикорм не входят — у них нет общей единицы измерения с молоком.

`typicalMl`/`refMin` берутся ОДИН РАЗ на все семь дней, а не
пересчитываются заново на каждый: иначе дни считались бы разными
весами модели и были бы несравнимы между собой.

Если пол ребёнка не задан (`perFeedMl` возвращает null), колонка
показывает число кормлений вместо миллилитров — так честнее, чем
выдавать оценку без веса.

### 4. Сцеживание одной груди как основа объёма

Поле «Утреннее сцеживание, 1 грудь» в карточке модели кормлений.
Заполнено — `perFeedMl` использует это значение НАПРЯМУЮ вместо
расчёта (суточный бюджет / число кормлений), как и просили. Пусто —
работает как раньше.

Две оговорки показываются прямо в интерфейсе, а не спрятаны:
- Помпа обычно извлекает меньше, чем эффективно сосущий ребёнок:
  в исследовании с контрольным взвешиванием (Kent et al., 2006)
  дети высасывали в среднем около 67 % молока, доступного в груди
  к началу кормления, с большим разбросом. Это значит, что
  сцеживание — скорее ОСТОРОЖНАЯ, чем завышенная оценка.
- Утренняя выработка обычно самая высокая за сутки, так что цифра
  может быть выше типичной дневной порции.

Оба параметра — расчётный и введённый — показываются рядом, чтобы
было видно, насколько они расходятся.

### 5. Метка «Внешняя причина» для укладывания

Третья кнопка в `SETTLE_KINDS` рядом с «Плакал»/«Был бодрый». Смысл
отличается принципиально: у «Плакал»/«Был бодрый» есть НАПРАВЛЕНИЕ
(окно упущено в такую-то сторону), у «Внешней причины» направления
нет — родитель говорит, что момент не отражает ни прогноз, ни
готовность ребёнка (гости, дорога, что угодно), и его нужно не
переклассифицировать, а вычеркнуть из выборки целиком.

Исключается из ВСЕХ мест, где по укладываниям считается точность или
обучается форма: `personalWindow` (подгонка прямой), `measureBias`
(смещение и разброс), `sourceScores`/`pickSource` (сравнение с
чужими таблицами — иначе один сорванный вечер портил бы оценку сразу
всех четырёх источников одинаково, пряча реальную разницу между
ними).

## Третий вид пушей: вехи развития

`web/src/milestones.js` — календарь, а не прогноз: возраст ребёнку
исполняется независимо от того, что записано в дневнике, поэтому
модуль детерминирован и БЕЗ ПАМЯТИ (тот же приём, что в `pickSource`):
одна и та же пара (дата рождения, ПДР) в один и тот же момент времени
всегда даёт один и тот же следующий пуш, не нужно хранить «какой по
счёту уже отправлен».

Источник — ежемесячная таблица навыков и красных флагов (от
фактической даты рождения) и список скачков развития по мотивам
концепции Wonder Weeks (строго от ПДР, если она известна, иначе от
даты рождения — с понятной потерей точности для родившихся не в
срок). Тексты переписаны в тёплом тоне и обходятся без
катастрофизации: это заметки для интереса и повод поговорить
с педиатром, а не диагностика.

Пропущенный триггер подхватывается в окне `CATCH_UP_MS` (3 дня) —
дальше считается, что момент упущен, переходим к следующему; иначе
после долгого простоя пришёл бы залп из полугода пушей разом.

### ПДР и её защита от устаревания

`households.due_at` — необязательное поле, LWW-профиль, как `birth`
и `sex`. Влияет только на скачки развития; ежемесячные вехи навыков
ПДР не используют.

Отдельный, второй механизм защиты рядом с `guard_type`/`guard_after`
(тот сверяется с таблицей событий): для вида `dev` уведомление несёт
СНИМОК дат — `guard_due_at`/`guard_birth_at`, значения на момент
расчёта. Перед отправкой сервер сравнивает снимок с ТЕКУЩИМИ
`households.birth`/`due_at`. Если родитель поправил ПДР уже после
того, как пуш был посчитан, — отправка отменяется, потому что скачок
целиком считается от другой даты.

Здесь был баг при реализации, который стоит запомнить как урок:
я дважды писал код, «который должен был сработать», но не проверял
исполнение до конца — `setNotification` не вставлял новые колонки
в SQL, а ответ `/api/sync` не возвращал `dueAt` вообще, хотя оба
патча были написаны и напечатали «готово». Обнаружилось только
прогоном настоящего цикла: создать семью → поставить пуш → сменить
ПДР → дождаться реального тика планировщика (не просто прочитать
код) → убедиться, что `sent` остался 0. Патч, который не проверен
сквозным прогоном, не патч.

## Проверка: шкала кормления во время сна

Родитель заметил, что шкала выглядит всегда полной, пока ребёнок
спит. Проверил построчно: математику (`stomachAt`/`predictFeed`) на
синтетике и на реальном экспорте дневника, включая кластерное
кормление перед сном и запись с нулевым объёмом, а также сам
ОТРИСОВАННЫЙ компонент `FeedNote` в разные моменты сна. Во всех
случаях процент и ширина полосы падают ожидаемо, например для
кормления грудью: 100 % → 65 % за 30 минут → 42 % за час → 17 % за
два часа. Бага в коде не нашёл.

Вероятное объяснение — не баг, а совпадение по времени: многие дети
засыпают вскоре после кормления (кормление как способ уложить), и
типичный дневной сон в этом возрасте (45–90 минут) заканчивается
раньше, чем шкала успевает опуститься сильно ниже половины — то есть
при взгляде именно во время сна она действительно чаще всего
«ещё прилично заполнена», это не значит «не двигается». Если после
этого разбора шкала всё ещё выглядит буквально неизменной несколько
часов подряд — стоит прислать конкретные цифры/скриншот с временем,
это будет говорить о другой, ещё не найденной причине.

## Найден настоящий баг: суточный объём медленно падал каждый день

Родитель заметил, что суточный объём кормления по возрасту потихоньку
уменьшается день ото дня, хотя в этом возрасте он должен расти.
Причина: между взвешиваниями `weightKg` держал вес БУКВАЛЬНО
замороженным на последнем измерении, а таблица мл/кг/сут (мета-анализ
по возрасту) МОНОТОННО убывает на всём диапазоне. Возраст растёт, вес
стоит на месте — суточный объём (вес × мл/кг) обязан был ползти вниз
каждый день, даже когда ребёнок растёт нормально:

    день взвешивания: 5.676 кг -> 711 мл/сут
    десять дней спустя, без нового взвешивания: те же 5.676 кг -> 699 мл/сут

При этом по медиане ВОЗ на том же отрезке возраста (2.3–4.3 мес)
суточный объём должен РАСТИ: 692 → 772 мл — вес обгоняет снижение
мл/кг с большим запасом.

**Исправление:** между взвешиваниями вес теперь не держится
константой, а ЭКСТРАПОЛИРУЕТСЯ вперёд вдоль того же перцентильного
канала ВОЗ — стандартное клиническое допущение, что здоровый ребёнок
держится примерно одной z-оценки, а не одного веса в кг. Считаем
z-оценку в момент измерения (`zOf`) и проецируем её на сегодняшний
возраст (`valueAt`). На тех же данных: с шестого дня после
взвешивания вес и суточный объём снова растут день за днём, а не
падают.

Экстраполяция не включается (используется голое последнее измерение,
как раньше), если:
- пол ребёнка не задан — без него z-оценку не посчитать;
- взвешивание или сегодняшний возраст за пределами таблицы ВОЗ;
- с последнего взвешивания прошло больше `WEIGHT_EXTRAPOLATE_MAX_DAYS`
  (60 дней) — два месяца без единого взвешивания сами по себе повод
  предложить взвесить ребёнка, а не тянуть канал ещё дальше без
  проверки.

## Разобрано: почему сон перед ночью «почти всегда сломан»

Гипотеза была про разбиение поправки по порядковому номеру сна
(1-й, 2-й, 3-й…). Проверка на реальных данных её не подтвердила —
но подтвердила саму жалобу, причём точнее, чем ожидалось.

**Порядковый номер не работает как признак.** За неделю дней с тремя,
четырьмя и пятью дневными снами было поровну — то есть 3-й сон в один
день оказывается последним перед ночью, а в другой день после него
идёт ещё один. Разбиение по номеру перепутало бы их.

**Настоящий признак — прогресс дня, и он уже есть в модели.** На тех
же данных сон, оказавшийся последним перед ночью, ВСЕГДА начинался
при прогрессе 0,68–0,83; любой другой дневной сон — не выше 0,63.
Это чистое разделение, и оно не требует знать заранее, окажется ли
сон последним: прогресс считается по времени НАЧАЛА сна, которое уже
известно в момент прогноза. Порог `LATE_NAP_THRESHOLD = 0.65` в
`sleep.js` лежит ровно между кластерами.

**И структурная разница подтвердилась количественно:**

    сон перед ночью:  медиана длины 28 мин  (n=7)
    остальные:        медиана длины 106 мин (n=20)

    промах прогноза перед ночью: медиана 13 мин, MAD 25
    промах прогноза в остальном: медиана 0 мин,  MAD 9

Почти вчетверо короче и почти втрое неустойчивее по прогнозу — жалоба
обоснована.

### Найденный и исправленный механизм

Штраф за короткий сон (`shortPenalty` в `predictWindow`) сравнивает
длину сна с `typicalNap` — медианой последних снов. Она была ПУЛОВОЙ,
без учёта времени суток: 28-минутную дрёму перед ночью сравнивало
с ориентиром в 94–103 минуты, собранным в основном по длинным утренним
снам. Доля от ориентира получалась 5–39% почти всегда — штраф
применялся у самой границы (15 минут) не потому, что сон был
недостаточным для СВОЕГО места в дне, а потому что сравнение шло не
с тем.

Исправлено: `typicalNap` теперь принимает необязательный `matchNap` —
сон, чью половину дня (до или после порога) нужно повторить в
выборке. Задействовано во всех трёх местах, где считается ориентир:
в живом прогнозе, в подгонке личной прямой по истории и в подсказке
на вкладке «Сейчас». Если своей истории в нужной половине дня ещё
меньше `MIN_SAMPLES` — используется прежний пуловый ориентир, рано
делить то, на что не набралось наблюдений.

### Честно об измеренном эффекте: он маленький

На вашей неделе (n=7) итоговый промах почти не изменился: медиана
13→12 минут, MAD 25→26. Разобрался, почему. `shortPenalty` входит в
формулу как `max(carryOver, shortPenalty)` — берётся большее из двух.
Для по-настоящему коротких снов (5–21 минут) недорассеянное давление
(`carryOver`) само уже близко к максимуму независимо от того, с чем
сравнивать длину, так что исправление ориентира там попросту ничего
не меняет — оно перекрыто. Из семи предсказаний изменились только два
(на 37- и 11-минутных снах, где `carryOver` не успевал перекрыть),
и на несколько минут, не радикально.

Крупные промахи (+67, +44, −42 минуты) не сдвинулись вовсе. Похоже,
дело не в недосыпе и не в неправильном ориентире, а в том, что момент
начала вечернего укладывания определяет не внутреннее давление сна,
а ваш собственный вечерний распорядок — купание, гости, кто во сколько
пришёл домой. Это не то, что предсказывается по дневнику ребёнка в
принципе.

Правку оставил — сравнивать дрёму перед ночью с дрёмами перед ночью,
а не с утренними снами, правильно независимо от того, меняет ли это
сегодняшние цифры. Но открытый вопрос остаётся: если у сна перед
ночью систематически больше необъяснимого разброса, может быть
разумнее дать этому окну отдельный, более широкий допуск (или
собственную поправку смещения, как сейчас разделено «утро/вечер»,
только на три части), — вместо того чтобы пытаться сузить его дальше
через более точные ориентиры. Это уже не багфикс, а решение, которое
стоит принимать осознанно: оно отчасти возвращает к вопросу о ширине
окна, который недавно закрывали в обратную сторону.

## Периоды болезни

Болезнь ломает сон: он фрагментируется, ребёнок засыпает вне ритма,
укладывания идут тяжело по причинам, к времени суток отношения не
имеющим. Если такие дни попадут в обучение, приложение запомнит их как
норму этого ребёнка.

Период задаётся ДАТАМИ начала и окончания, а не таймером «заболел
сейчас / выздоровел сейчас»: болезнь обычно отмечают задним числом,
когда уже понятно, что это была она. Окончание можно оставить пустым —
тогда период открытый. День окончания входит в период целиком
(до 23:59:59).

Отметка ставится РУКАМИ и намеренно не определяется автоматически:
детектор аномалий не отличил бы болезнь от настоящего сброса сна,
а следовать за сбросом приложение как раз должно.

Хранится как событие типа `illness` со `start` и `end` (незакрытое —
«болеет сейчас»), то есть едет по обычной синхронизации и видно обоим
родителям. Тип добавлен и в белый список сервера: неизвестные типы там
молча превращаются в `feed`, поэтому список нужно расширять
одновременно с клиентом.

Что исключается и что нет:

- исключается — `measureBias`, `typicalNap`, `settleShare`,
  `settleStats`, `medianNapIn`. Всё, что описывает НОРМУ ребёнка.
- НЕ исключается — `carryOver`. Ребёнок действительно спал, давление
  действительно рассеялось: это физика последних часов, а не суждение
  о норме.
- НЕ исключается — показ снов на вкладках «День» и «Неделя». Записи
  настоящие, прятать их незачем. А вот САМА запись `illness` из списка
  записей дня исключена: это период, а не событие дня. Раньше она туда
  попадала и показывалась как «Подгузник», потому что в `eventTitle`
  не было ветки по умолчанию и любой незнакомый тип падал в последнюю
  ветку цепочки.

Прогон: 30 дней нормы, 6 дней болезни (сон вдвое короче и вразнос),
затем выздоровление.

    день после выздоровления   без отметки   с отметкой
    1                                 −41            4
    3                                 −26           −1
    5                                 −18           −5
    8                                   4            2

Без отметки прогноз возвращается к норме примерно через неделю, потому
что `settleShare` держит семидневное окно, а медиана дневного сна
проседает с 95 до 57 минут. С отметкой сбоя нет вовсе.

## Предохранитель по сырому расхождению

`measureBias` считает две оценки: с учётом меток и сырую, по всем
дневным засыпаниям без разбора. Если фильтры по меткам съели почти все
наблюдения, а сырое расхождение при этом не меньше `RAW_ALARM = 30` мин,
приложение опирается на сырое — значит возрастная таблица просто не про
этого ребёнка. Это страховка против собственных фильтров.

Множитель доверия при этом продолжает действовать: при сплошном «плакал»
предохранитель даёт ноль и перебить защиту от петли обратной связи
не может.

Демпфирование живёт ТОЛЬКО в `autoBias`. Кламп границ в `predictWindow`
симметричен намеренно: два множителя в разных местах формулы гасили бы
положительный сдвиг вложенно и непредсказуемо.

Минимум наблюдений для любой статистики — `MIN_SAMPLES = 4`, одно число
на все проверки (раньше здесь были вразнобой 3, 4 и 5 без оснований для
разницы). Единственная точка сборки прогноза — `predictNext`; отдельной
`effectiveBias` больше нет, она дублировала ту же сборку вторым куском
кода и могла разойтись молча.

Приложение намеренно ничего не утверждает про «перегул»: доказательная
база вокруг этого понятия спорная, часть специалистов считает его мифом,
а часть исследований связывает высокое давление сна с более быстрым
засыпанием, а не с сопротивлением ему. Метка описывает наблюдаемое
(насколько тяжело прошло укладывание), а не механизм.

Возрастная таблица ограничивает прогноз диапазоном [lo-30, hi+30], но
эти границы раздвигаются на величину поправки. Иначе ребёнок с окнами
выше таблицы упирался бы в потолок, и приложение молча выбрасывало бы
то, что само же измерило.

Средние за неделю считаются только по полным суткам: первый день ведения
дневника всегда начат с середины, а сегодняшний ещё не закончился.
Оба выбрасываются — но только если после этого остаётся хоть один день.
